# v0.6 Handoff Bus + Mission Orchestrator — CHAT 04

Status: **IMPLEMENTED FOR BOUNDED ORCHESTRATION LAYER**  
Date: 2026-10-01  
Baseline: `main@7e44ada03eaeb01db1b9b28385c5be843877df41`

CHAT 04 turns a validated Mission Plan into bounded runtime-neutral execution.

It introduces typed handoff envelopes, bounded DAG orchestration, Execution Attempt provenance, dependency/failure propagation, and cooperative cancellation.

It does **not** introduce a Model Router, a Tool Router replacement, public live endpoints, automatic external writes, or broad autonomous recovery.

## 2. Typed outbound handoff

A handoff envelope binds one Mission TaskNode to one destination employee.

It contains:

- handoff ID;
- Mission ID;
- TaskNode ID;
- upstream/source TaskNode IDs;
- upstream/source employee IDs;
- destination employee;
- objective;
- effective constraints;
- required evidence;
- upstream artifact references;
- Mission-shared budget envelope;
- risk class;
- allowed runtime capabilities;
- required skills;
- bounded timeout;
- timestamp.

The canonical source kind is:

```text
MISSION_ORCHESTRATOR
```

Root tasks have no upstream source tasks/employees.

Dependent tasks receive source TaskNode/employee identities from the graph.

## 3. Typed handoff return

The return envelope contains:

- handoff ID;
- Mission ID;
- TaskNode ID;
- employee ID;
- state;
- artifact references;
- evidence references;
- explicit unknowns;
- residual risks;
- optional signed receipt reference;
- error category;
- finish timestamp.

Allowed return states are:

```text
SUCCEEDED
FAILED
PARTIAL
BLOCKED
CANCELLED
```

A handoff return is execution output/provenance.

It is not by itself independent verification.

## 4. Manual-handoff compatibility projection

`renderManualHandoffCompatibilityDraft(...)` provides a bounded owner-readable projection.

The draft explicitly says:

```text
DRAFT_NOT_SENT
NOT_EXECUTED
NOT_VERIFIED
```

It also states that the projection is:

- not an `operations/handoff` Hermes packet;
- not runtime evidence;
- not a delivery receipt.

This preserves the old manual handoff safety semantics without pretending the new Mission envelope is an official Hermes task.

## 5. Runtime-neutral dispatch

The orchestrator does not know Hermes, Codex, or another provider directly.

The caller supplies:

```text
resolveRuntime({ mission, task, node_meta })
```

The resolution supplies:

- runtime execution adapter;
- execution policy;
- required runtime capabilities;
- optional future model-route reference;
- optional capability-route references;
- unknowns;
- residual risks.

The actual execution still goes through:

```text
packages/runtime-execution-adapter
  -> prepare
  -> bounded execute
  -> normalize result
  -> collect evidence
  -> cleanup
```

The orchestrator therefore consumes the existing runtime-neutral safety boundary instead of bypassing it.

## 6. Mission execution flow

For an executable TaskNode:

```text
PLANNED
  -> READY
  -> typed handoff
  -> RUNNING
  -> bounded runtime outcome
  -> immutable Attempt
  -> SUCCEEDED / FAILED / PARTIAL / BLOCKED
```

For high-impact work without approval:

```text
PLANNED
  -> WAITING_APPROVAL
  -> STOP
```

The runtime resolver is not called for an approval-blocked task.

## 7. Attempt provenance

Every bounded dispatch receives a new Attempt ID.

An Attempt records:

- TaskNode ID;
- ordinal;
- runtime identity;
- future model-route ref when supplied;
- capability-route refs;
- start/finish timestamps;
- outcome state;
- error category;
- cleanup result;
- evidence/artifact refs;
- optional signed receipt ref.

CHAT 04 does not create fake receipt references.

If no signed receipt provider is supplied, the Attempt receipt remains `null`.

## 8. Pre-execution rejection semantics

An important distinction is preserved:

```text
runtime contract/policy rejected dispatch
!=
runtime executed and failed
```

If the bounded runtime wrapper rejects the dispatch before producing a runtime outcome—for example because the TaskNode requests an undeclared capability—the orchestrator records a:

```text
BLOCKED Attempt
```

with the explicit contract/policy error category.

It does **not** label that event as a runtime `FAILED` execution.

Downstream tasks are then blocked by dependency.

## 9. Dependency propagation

A TaskNode only becomes runnable when all upstream dependencies are:

```text
SUCCEEDED
or
VERIFIED
```

If an upstream dependency becomes:

```text
FAILED
PARTIAL
BLOCKED
CANCELLED
```

the dependent task becomes:

```text
BLOCKED
blocking.kind = DEPENDENCY
```

Dependency blocking is propagated until a fixed point, so ordering of TaskNodes in the original input cannot hide a deeper blocked descendant.

## 10. Bounded concurrency

`executeMissionPlan(...)` accepts:

```text
maxConcurrency = 1..8
```

The orchestrator:

1. calculates currently runnable TaskNodes;
2. takes at most `maxConcurrency`;
3. executes that batch concurrently;
4. records results;
5. propagates blockers;
6. calculates the next frontier.

The canonical synthetic acceptance test uses four TaskNodes:

```text
Alex research -----\
                    -> Praroro synthesis -> Siti verification task
Nara analysis -----/
```

Alex and Nara run concurrently with observed maximum active concurrency = 2.

Praroro waits for both.

Siti waits for Praroro.

The Mission ends:

```text
SUCCEEDED
```

not `VERIFIED`.

Independent Mission-level verification remains a separate truth boundary.

## 11. Artifact/evidence flow

Artifacts produced by an upstream Attempt are included as:

```text
input_artifact_refs
```

in downstream handoffs.

Example:

```text
research artifacts --\
                     -> synthesis handoff inputs
analysis artifacts --/
```

Evidence/artifact references are also aggregated into the final Mission projection.

This does not create an Artifact Workspace yet; durable artifact registry/versioning is a v0.6.1 milestone.

## 12. Mission settlement

Current aggregate settlement rules:

- all required TaskNodes `SUCCEEDED/VERIFIED` -> Mission `SUCCEEDED`;
- unresolved approval -> Mission `WAITING_APPROVAL`;
- any `PARTIAL` -> Mission `PARTIAL`;
- failure with no useful success -> Mission `FAILED`;
- failure/block after useful success -> Mission `PARTIAL`;
- blocks with no useful success -> Mission `BLOCKED`;
- explicit cooperative cancellation -> Mission `CANCELLED`.

Mission `SUCCEEDED` does not imply Mission `VERIFIED`.

## 13. Cancellation boundary

CHAT 04 supports **cooperative cancellation between scheduling frontiers/batches**.

If cancellation is requested:

- TaskNodes that have not started are moved to `CANCELLED`;
- no new runtime dispatch is made;
- Mission becomes `CANCELLED`.

Current runtime execution adapter does not expose an external hard-abort signal to the Mission Orchestrator.

Therefore CHAT 04 does **not** claim it can instantly kill a TaskNode that is already in-flight.

An in-flight bounded task must settle through its timeout/cleanup contract before the next scheduling decision.

This limitation is explicit rather than hidden.

## 14. Synthetic acceptance cases

CHAT 04 tests cover:

### Successful DAG

- 4 TaskNodes;
- 2 parallel roots;
- 4 Attempts;
- 4 handoffs;
- 4 handoff returns;
- upstream artifact propagation;
- bounded runtime cleanup;
- Mission `SUCCEEDED`;
- no false Mission `VERIFIED`.

### Upstream failure

- root executes once and fails;
- child becomes dependency-blocked;
- grandchild becomes dependency-blocked;
- no downstream runtime call;
- Mission settles truthfully.

### Approval gate

- paid-action root remains `WAITING_APPROVAL`;
- runtime resolver call count = 0;
- Attempt count = 0.

### Cooperative cancel

- first safe parallel batch succeeds;
- cancel signal is observed before next frontier;
- unstarted synthesis/verification tasks become `CANCELLED`;
- Mission becomes `CANCELLED`.

### Runtime contract rejection

- invalid/undeclared execution capability is rejected;
- Attempt is `BLOCKED`, not falsely `FAILED`;
- dependent task is dependency-blocked;
- Mission becomes `BLOCKED`.

## 15. What CHAT 04 intentionally does not do

CHAT 04 does not:

- choose models dynamically;
- implement Model Router;
- replace capability-router;
- perform external-write connectors;
- auto-approve high-impact work;
- independently verify Mission success;
- retry failed TaskNodes;
- resume from checkpoints;
- hard-cancel in-flight runtime processes;
- expose an internet/public execution API;
- claim production reliability from synthetic fixtures.

## 17. CHAT 05 handoff

CHAT 05 may now implement:

**Model Router**

The Model Router should select a permitted model/runtime class before the orchestrator calls the bounded runtime adapter.

Inputs should include:

- task class;
- latency target;
- modality;
- reasoning requirement;
- privacy/locality requirement;
- context requirement;
- budget;
- provider health;
- user policy;
- fallback permission.

CHAT 05 must preserve:

```text
model route decision != execution
runtime connected != authorized
fallback != permission to violate privacy
SUCCEEDED != VERIFIED
```

The orchestrator already has a `model_route_ref` slot so CHAT 05 can integrate without rewriting Attempt identity.
