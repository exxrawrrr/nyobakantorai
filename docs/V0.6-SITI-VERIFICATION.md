## Purpose

CHAT 10 operationalizes independent verification without creating a second evidence system or a second task state machine.

The canonical boundaries remain:

- `packages/evidence-verifier/` for evidence decisions;
- `packages/task-registry/task-node.mjs` for TaskNode state truth;
- `packages/mission-engine/contracts.mjs` for Mission state truth;
- `config/employees.json` for independent reviewer policy;
- CHAT 09 telemetry for execution facts.

Siti is the default verifier when the assignee's canonical policy allows Siti. Siti cannot verify Siti's own production work; another registry-approved reviewer must be used.

## Structured outcomes

The engine uses the existing verification vocabulary:

Claim verdicts:

- `SUPPORTED`
- `CONTRADICTED`
- `NOT_VERIFIED`

Review states:

- `PASS`
- `FAIL`
- `INCOMPLETE`

Only `PASS` may produce decision `VERIFIED`.

`FAIL` and `INCOMPLETE` produce `NOT_VERIFIED` and leave the canonical TaskNode at `SUCCEEDED`.

## Research verification

A research claim checks:

- source reference exists;
- source exists;
- source is relevant;
- source is current enough;
- expected and observed values match;
- expected and observed units match.

Direct mismatch becomes `CONTRADICTED`.

Unavailable, stale, irrelevant, or unobserved facts remain `NOT_VERIFIED` / `INCOMPLETE` rather than being softened into PASS.

## Code verification

A code review records:

- declared changed files;
- inspected changed files;
- test results;
- regression checks;
- negative checks;
- fix-claim-to-evidence mappings;
- remaining unknowns.

A failed regression/negative/test check is a contradiction.

A missing inspection, missing check, NOT_RUN check, or missing evidence remains an unknown/incomplete condition.

## External-state verification

External state is checked through an injected read-only hook.

The hook receives a frozen request containing:

- task and mission identity;
- assignee identity;
- actual verifier identity;
- target reference;
- expected state.

The hook cannot directly grant `VERIFIED`.

Accepted observed states are:

- `MATCH`
- `CONTRADICTED`
- `UNKNOWN`

A missing hook, hook failure, missing read-back evidence, missing timestamp, or UNKNOWN state prevents PASS.

A contradictory read-back remains visible and prevents VERIFIED.

## Independence

The verifier identity is checked against the assignee's canonical `verification_policy`.

The engine rejects:

- self-verification;
- verifier IDs outside the reviewer allowlist;
- missing independence policy;
- attempts to rely on actor identity as proof.

Siti's own tasks therefore require another registry-approved reviewer, such as the reviewer candidates already defined for Siti in the workforce registry.

## Canonical state promotion

The verifier starts from a canonical `SUCCEEDED` TaskNode.

Only a `PASS` review may call the canonical transition:

`SUCCEEDED -> VERIFIED`

The verification reference is added as evidence.

The Mission Orchestrator exposes an optional `buildVerificationRequest` hook.

That hook supplies verification inputs only. Caller-provided fields such as a fake `decision: VERIFIED` or forged TaskNode are ignored because the Orchestrator injects the canonical TaskNode into `runSitiVerification`.

If every final TaskNode is independently `VERIFIED`, Mission may use the existing canonical transition:

`SUCCEEDED -> VERIFIED`

with `verification_satisfied=true`.

Without a verification hook, existing behavior is unchanged: tasks and Mission remain `SUCCEEDED`.

## Content-addressed verification record

Each review receives:

`verification:sha256:<digest>`

`validateSitiVerificationRecord(...)` recomputes the digest before a review record is reused.

A modified review state, decision, contradiction set, unknown set, or other digested content fails validation.

## Public Evidence UI

A valid live response may include an optional canonical verification sidecar.

When present, the public boundary validates:

- verification-record digest;
- task binding;
- mission binding;
- assignee binding.

The public projection exposes only bounded safe fields and applies the same private/sensitive-reference redaction used by execution telemetry.

The Evidence UI shows:

- verifier;
- independence;
- review kind;
- PASS / FAIL / INCOMPLETE;
- VERIFIED / NOT_VERIFIED decision;
- claim verdicts;
- contradictions;
- unknowns;
- verification reference.

Runtime truth and verification truth remain separate.

A real runtime may be `LIVE_RUNTIME` while the independent correctness review is `FAIL / NOT_VERIFIED`; the contradiction remains visible.

Synthetic and LIVE_UNAVAILABLE responses cannot surface injected verifier results.
