# v0.4 Review & Release Map

This document is the human review map for PR #11. It exists because the implementation branch is large enough that commit-by-commit reading is no longer a useful way to understand product truth.

## Architecture freeze

Until the evidence-dependent v0.4 gates are resolved or deliberately deferred, do not add new workers, random frameworks, memory providers, or abstraction layers unless a failed evaluation creates a concrete requirement.

The current priority is:

```text
prove existing behavior
-> publish failures and limits
-> fix evidence-backed gaps
-> release
```

## Branch and release topology

Current intended topology:

```text
main
  -> latest stable/public release

prd/next-modular-workforce
  -> staging/design base for the modular-workforce program

v0.4/modular-workforce
  -> implementation candidate for PR #11
```

PR #11 intentionally targets `prd/next-modular-workforce` while the implementation is still a candidate. Merging PR #11 into that staging branch must **not** be described as shipping v0.4 to users.

Before a stable v0.4 release, the reviewed candidate must be promoted to `main` through an explicit PR/merge path and then pass the release gates from the final main-based commit. A tag/release must point to the promoted stable commit, not only to the staging branch.

### Evidence status after Phases 1–6

Controlled/deterministic evidence now exists for:

- signed-receipt freshness/replay/binding/runtime-trust negative cases with zero false-success;
- local memory isolation + M3 reviewer provenance guards;
- 16-worker personality-governance invariance;
- controlled live-model Fikri semantic/source/downstream evaluation on the recorded synthetic fixture set;
- Playwright MCP controlled live browser evaluation.

Still intentionally unproven or incomplete:

- live cross-harness Hermes/Gemini/Copilot behavioral parity;
- Cognee profile-isolation/export/deletion evaluation (`NOT_RUN / UNPROVEN`);
- Browser Use live evaluation, therefore the Playwright-vs-Browser-Use head-to-head remains open;
- >=20-case real-task baseline: currently `COLLECTING` at 1/20 eligible direct owner tasks;
- broad real-workflow coverage across major departments.

Do not convert these states to green because scaffolding or one-sided provider evidence exists.

## Claim vocabulary

Use this progression consistently:

```text
IMPLEMENTED
-> DETERMINISTICALLY_VERIFIED
-> REAL_WORLD_EVALUATED
```

And preserve the capability truth boundary:

```text
cataloged != installed != connected != authorized != executed != succeeded != verified
```

## Storage checkpoint

The storage core now has:

- a Web-Storage-compatible adapter boundary;
- an in-memory adapter for deterministic tests;
- portable storage bundle export/import primitives;
- SHA-256 payload integrity;
- registry validation on import;
- supported-settings normalization;
- tamper and invalid-registry tests.

This does **not** yet mean the office UI/application has completed migration to the new storage boundary. ROADMAP therefore keeps the broader storage item open until wiring/migration is finished.

## Merge/release checklist

Current release decision: **HOLD stable promotion**. See `docs/V0.4-RELEASE-DECISION.md`.

Before calling v0.4 stable:

1. PR #11 remains draft while the currently deferred evidence scope has not been re-approved for release.
2. `NOT_RUN / UNPROVEN` stays truthful unless a real run with evidence exists.
3. Static cross-harness exports are described as packaging compatibility only.
4. Runtime policy is described as application-level sandboxing, not OS isolation.
5. Signed receipts are described as authenticity/integrity evidence, not proof that the external world matches the payload.
6. The initial 20-case dataset is described as a baseline, not general statistical proof.
7. Failures are published with PASS/FAIL/WHY/RECOVERY/EVIDENCE.
8. The final candidate is explicitly promoted to `main` through an intentional future decision.
9. CI/release gates are rerun from the final promoted commit.
10. Temporary PRD/workplan requirements are durably represented in permanent docs before the temp files are removed.
