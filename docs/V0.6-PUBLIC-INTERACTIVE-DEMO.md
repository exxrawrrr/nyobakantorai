## Purpose

CHAT 08 adds a public-facing product experience without weakening the existing local/runtime safety boundaries.

The UI exposes two intentionally different actions:

- `TRY DEMO` — deterministic, synthetic, no login, no external model dependency.
- `TRY LIVE AI` — may be labeled live only when an injected runtime result passes the existing Live Sandbox record contract.

Synthetic work is never promoted to live evidence.

## Backend surface

The office server exposes:

- `GET /api/public/capabilities`
- `POST /api/public/session`
- `POST /api/public/demo`
- `POST /api/public/live`

The server remains bound to localhost in CHAT 08. "Public" here describes the product/UI contract; it does not claim public Internet deployment.
## Anonymous session boundary

A session is in-memory and disposable.

The browser receives an opaque cookie:

- `HttpOnly`
- `SameSite=Strict`
- `Path=/`
- 30-minute max age

The raw session token is not returned in the JSON body and is not stored in localStorage.

Default limits:

- 1 active mission per anonymous session;
- 8 deterministic demo missions per session;
- 1 live mission per session;
- 12 requests per rolling 60 seconds;
- 1,200 objective characters;
- at most 4 planned TaskNodes;
- at most 200 in-memory sessions before bounded pruning.

Request JSON is capped at 8 KiB by the HTTP boundary.

## Deterministic demo

The demo composes the existing Mission Planner rather than creating another task domain.

For the same objective it uses a fixed planning clock and content-derived IDs, so the public synthetic plan is reproducible.
Every demo plan is forced to:

- `READ_ONLY`;
- guarded autonomy;
- no account access;
- no production external writes;
- no paid actions;
- no destructive actions;
- explicit `SYNTHETIC` truth labels.

The response includes the Mission Plan and a presentation projection with visible task layers and assigned employees.

## Live truth gate

The public-demo service accepts a live runner only as an injected internal dependency.

A result becomes `LIVE_RUNTIME` only when all of the following are true:

- the runner reports execution;
- the runtime outcome reports success;
- the Sandbox Record validates against its content-addressed digest;
- Mission and TaskNode identity match the current public plan;
- sandbox status is `PASS`;
- quota status is `PASS`;
- teardown is verified;
- execution_ok is true.

Anything else is not a live success.

The current office server does not inject an arbitrary-mission live runner. Therefore `POST /api/public/live` currently returns `LIVE_UNAVAILABLE` with an explicit deterministic-demo fallback rather than fabricating live execution.
## UI contract

The new `Try AI` view provides:

- objective input;
- separate `TRY DEMO` and `TRY LIVE AI` actions;
- explicit `SYNTHETIC DEMO`, `LIVE RUNTIME`, or `LIVE UNAVAILABLE` state;
- anonymous-session quota summary;
- layered TaskNode / employee visualization;
- deterministic-demo fallback button when live is unavailable;
- responsive single-column behavior at mobile width.

Untrusted mission text is rendered through DOM text nodes rather than injected HTML.

## Security / scope notes

CHAT 08 does not:

- expose the localhost office server to the Internet;
- add provider credentials;
- read user accounts;
- enable production external writes;
- enable paid or destructive actions;
- turn an unavailable runtime into synthetic "live" output;
- replace the canonical Mission Planner, Live Sandbox, or task registry.

Internet deployment, if later authorized, requires its own hosting, abuse, TLS/cookie, and deployment-boundary review.
