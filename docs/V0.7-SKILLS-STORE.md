## Goal

CHAT 21 upgrades the current 16-person workforce before adding headcount.

The core authority boundary is:

```text
skill available
!= skill installed
!= skill attached
!= tool installed
!= connector connected
!= provider permission
!= execution permission
!= verified result
```

Skills are procedural capability only.

They never grant connector, tool, provider, account, or mutation authority by themselves.

## Canonical catalog

The Skills Store reads canonical skills from:

`skills/canonical/*/SKILL.md`

Catalog implementation:

`packages/skills-store/index.mjs`

Catalog entries bind:

- skill ID;
- exact semantic version from `metadata.nyoba-version`;
- SHA-256 of the full canonical `SKILL.md`;
- description;
- compatibility note;
- provenance mode;
- source IDs;
- pinned source commits/licenses;
- authority effect: `NONE`.

The catalog itself is content-addressed:

`skill-catalog:sha256:<digest>`

## Provenance

Canonical skill provenance remains sourced from:

- `config/skill-provenance.json`;
- `config/upstream-sources.json`.

Project-authored skills use:

`project:nyobakantorai`

with MIT license metadata.

Recreated/adapted skills retain their reviewed upstream source IDs and pinned source commit/license records.

A skill installation fails validation if:

- exact catalog version no longer exists;
- canonical content SHA drifts;
- provenance refs drift;
- authority effect is anything other than `NONE`.

## Install contract

`installSkill(...)` creates an immutable installation record:

`skill-install:sha256:<digest>`

Installations require:

- exact skill ID;
- exact version;
- content hash from the canonical catalog;
- provenance refs;
- owner actor;
- timestamp;
- evidence ref;
- `authority_effect: NONE`.

A worker cannot self-install a skill.

Installation input is rejected if it attempts to include:

- capability scope;
- connector grants;
- capability grants;
- permissions;
- toolsets;
- external capabilities;
- optional integrations;
- approval-policy changes;
- autonomy changes.

## Attach contract

`attachSkill(...)` creates:

`skill-attachment:sha256:<digest>`

Attachment binds:

- employee;
- exact installed skill/version;
- installation ref;
- owner actor;
- timestamp;
- evidence ref;
- authority snapshot SHA-256;
- `authority_effect: NONE`.

A worker cannot self-attach a skill.

Skill attachment is allowed to extend only the employee's effective procedural skill list.

These fields are preserved across attachment:

- `operational_contract.capability_scope`;
- `preferred_toolsets`;
- `external_capabilities`;
- `optional_integrations`;
- `approval_policy`;
- `verification_policy`;
- `memory_boundary`.

If any preserved authority field changes, attachment resolution fails closed.

## Employee packs

Standalone employee packs now apply Skills Store attachments as a distribution overlay.

The canonical employee registry remains the baseline authority source.

Pack generation:

1. copies the baseline Hermes employee profile;
2. resolves owner-reviewed Skills Store attachments;
3. copies only the attached canonical skill directories into the pack;
4. records baseline skills separately from effective skills;
5. records installation/attachment refs;
6. records `authority_effect: NONE`;
7. generates normal SHA-256 pack checksums.

Example:

Siti's baseline registry does not contain `nyoba-research-synthesis`.

Her CHAT 21 pack does.

Her connector/tool/capability authority is unchanged.

## New employee #17 rule

`scripts/new-employee.mjs` now requires:

`--capability-gap="..."`

The gap must explain why the need cannot be solved merely by attaching an existing reusable skill to an existing employee.

Generic headcount reasons such as:

- "more capacity";
- "extra help";
- "need more people";

are rejected.

Recommended order:

```text
inspect existing employee
  -> inspect reusable skill
  -> attach/version skill if sufficient
  -> measure capability loop
  -> document remaining capability gap
  -> only then add headcount
```

This keeps workforce growth capability-driven rather than headcount-driven.

- Capability Router;
- Connector Center;
- Approval Center 2.0;
- Browser Agent scopes;
- Cost Governor;
- Mission Engine;
- evidence verifier;
- runtime/provider state;
- human owner authority.

A Google Ads skill attached to a worker still cannot use Google Ads unless all normal capability, connector, resource, approval, and evidence gates pass.

Likewise, a browser skill cannot connect Playwright, inherit cookies, or authorize browser mutation.

## Claim boundary

CHAT 21 proves repository-level modular skill lifecycle and 16-employee procedural upgrades.

- external skills were installed from an unreviewed marketplace;
- any connector/provider became connected because of skill attachment;
- attached skills independently grant runtime tools;
- a worker can self-grant permissions;
- every skill has proven behavioral parity across every external agent harness.
