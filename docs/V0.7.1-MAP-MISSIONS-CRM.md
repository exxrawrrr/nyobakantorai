## Goal

Turn CHAT 23–24 verified geo research into operational lead intelligence without creating a hidden write/send path.

The core boundary is:

```text
verified geo profile
  -> CRM-ready candidate
  -> map/qualification/watchlist/territory artifacts
  -> draft CRM/outreach action
  -> owner approval
  -> separate execution layer

candidate != CRM write
draft != send
map display != provider-data retention permission
```

## Verified CRM candidates

A CRM candidate can only be created from a complete CHAT 24 bundle:

- provenance-aware business profile;
- explainable versioned score;
- exact profile/score Siti binding;
- Siti `PASS / VERIFIED`;
- finalized `VERIFIED_PROFILE`.

The CRM candidate carries:

- deterministic lead identity;
- profile/verified-profile refs;
- Place ID when available;
- resolved public fields only;
- score + model version;
- qualification tier;
- verification ref;
- source refs/types;
- created/updated timestamps.

It explicitly starts as:

`external_write_state = NOT_WRITTEN`

Provider-only fields such as raw payloads, Google-provider coordinates, reviews, photos, Maps URI, paging token, and provider attribution payload are forbidden in CRM candidates.

## Qualification visualization

Qualification tiers are deterministic and policy-versioned:

- A: 80–100 — high priority
- B: 60–79 — qualified
- C: 40–59 — watch / nurture
- D: 0–39 — low priority

Visualization is derived from verified candidates only.

A score band is a workflow aid, not a claim that the company will buy, reply, or convert.

## Map Mission data

A Map Mission combines verified CRM candidates with map presentation features.

Two retention modes exist.

### Google/provider location

`EPHEMERAL_PROVIDER`

Requirements:

- coordinates may be used in the active presentation view;
- Google Maps attribution is required;
- feature is `persistable=false`;
- durable map summary strips latitude/longitude;
- CRM export never receives those coordinates.

### Public durable location

`PUBLIC_DURABLE`

Requirements:

- source ref must belong to the verified candidate provenance;
- public-source policy must allow the retained data;
- no provider-retention bypass.

A Map Mission never claims exhaustive coverage.

## Office Geo Intel view

The Office now includes a **Geo Intel** view.

It renders:

- bounded mission title;
- verified lead count;
- qualification tier cards;
- map-feature lead cards;
- attribution warning when Google-provider features are present.

The UI explicitly shows:

- `WRITE ACTIONS: OFF`
- `EXHAUSTIVE: NO`
- `AUTO OUTREACH: OFF` in the empty-state boundary.

The view accepts a local view-model payload through the application integration and does not itself execute CRM writes or outreach.

## CRM-ready export

`createCrmReadyExportPack(...)` produces:

- `crm-leads.csv`
- `crm-leads.xlsx`
- `crm-evidence.json`

The pack contains only verified CRM allowlisted fields.

The evidence manifest records:

- candidate refs;
- verification refs;
- source refs;
- lead count;
- verified-only state;
- `outreach_included=false`;
- `external_write_performed=false`;
- `completeness_claim=false`.

Creating an export pack does not write to any CRM.

## CRM import approval

A CRM import requires an Approval Center 2.0 request with:

- target type `CRM_IMPORT`;
- risk `EXTERNAL_WRITE`;
- exact action `crm.import`;
- exact resource `crm-dataset:<crm_export_ref>`;
- evidence refs;
- human-readable import preview;
- explicit expiry.

Approval for CRM import cannot authorize outreach.

Approval remains permission, not execution evidence.

## Watchlist / change monitoring

The watchlist stores:

- lead/profile/candidate refs;
- Place ID;
- hashes of monitored durable CRM fields;
- budget;
- cadence;
- no raw provider content.

It does not store provider response snapshots.

A watchlist schedule is materialized through the normal Scheduler + Cost Governor path.

Current constraints:

- interval: 1–30 days;
- max 500 entries;
- bounded per-run hard cost;
- READ_ONLY mission risk;
- explicit constraints:
  - no outreach;
  - no CRM write;
  - no raw provider persistence;
  - reviewed geo/public-source policy only.

Change records store field names and before/after hashes plus evidence refs.

## Competitor radar

Competitor radar accepts only verified CRM candidates.

Roles:

- `COMPETITOR`
- `TARGET`
- `PARTNER`
- `UNKNOWN`

A `COMPETITOR` classification requires evidence.

The radar never infers competitor status silently from proximity or score.

## Territory planning

Territory planning reuses CHAT 23 Geo Core rectangle validation.

Requirements:

- explicit bounded rectangles;
- maximum 25 territories;
- bounded leads per territory;
- map features from the active Map Mission;
- no exhaustive-coverage claim.

Ephemeral provider coordinates may be used for current-session assignment, but the durable territory plan stores lead refs and user-defined territory geometry rather than copying provider coordinate payloads into CRM.

## Outreach drafts only

CHAT 25 exposes:

- `createOutreachDraft(...)`
- `createOutreachApprovalRequest(...)`

It intentionally does **not** expose:

- `sendOutreach(...)`
- `executeOutreach(...)`
- `writeCrm(...)`

An outreach artifact starts as:

- `state = DRAFT_ONLY`
- `automatic_send_allowed = false`
- `send_authorized = false`

Approval scope is exact to:

`outreach.send.<channel> -> outreach-draft:<draft_ref>`

Approval for one draft cannot authorize another draft.

Actual delivery belongs to a separate connected execution layer and requires execution evidence.
