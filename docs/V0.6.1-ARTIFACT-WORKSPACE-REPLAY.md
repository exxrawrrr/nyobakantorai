## Goal

CHAT 14 turns Mission outputs and execution history into durable production records that survive outside chat history.

The design intentionally keeps ownership boundaries intact:

- Mission Engine owns Mission / TaskNode / Execution Attempt and execution events;
- Artifact Workspace owns immutable artifact versions, payload checksums, provenance, and storage durability;
- Replay consumes canonical records and produces a structured timeline;
- Replay does not ask a model to narrate what happened.

## Artifact record

Each artifact version contains:

- stable `artifact_id`;
- integer `version`;
- type;
- media type;
- ownership;
- provenance;
- content SHA-256;
- byte length;
- payload encoding;
- previous-version reference;
- record SHA-256;
- content-addressed `artifact_ref`;
- creation timestamp.

Reference shape:

```text
artifact:<artifact-id>:v<version>:sha256:<record-sha256>
```

The artifact record checksum covers metadata including ownership, provenance, content checksum, and version ancestry.

Changing metadata without updating the canonical record makes validation fail.

Changing payload bytes makes payload validation fail.

## Artifact types

CHAT 14 provides canonical fixture coverage for:

- `REPORT`
- `DATA`
- `CODE`
- `IMAGE`
- `EVIDENCE`

Payload encoding can be:

- `utf8`
- `base64`

Binary image fixtures therefore do not require pretending binary content is text.

## Immutable versioning

Artifact content is never overwritten in place through the workspace API.

Writing the same `artifact_id` again creates the next version:

```text
v1 -> v2 -> v3 ...
```

Every version after v1 must reference the exact previous `artifact_ref`.

Workspace verification rejects:

- missing previous version;
- version gap;
- wrong artifact lineage;
- duplicate artifact ref;
- record/ref identity mismatch.

Old versions remain readable.

## Mission / Task / Attempt ownership

Every artifact requires a Mission owner.

Optional task and attempt ownership are explicit:

```text
Mission
  -> TaskNode
      -> Execution Attempt
          -> Artifact Version
```

`validateArtifactOwnership(...)` checks canonical relationships:

- artifact Mission matches Mission record;
- referenced TaskNode exists and belongs to that Mission;
- artifact employee matches TaskNode assignee when declared;
- referenced Attempt exists;
- Attempt belongs to the declared TaskNode.

Ownership mismatch is rejected rather than silently repaired.

## Provenance

Artifact provenance records:

- `source_kind`: `RUNTIME | USER | DERIVED | IMPORT | SYSTEM`;
- `source_refs`;
- `created_by`.

Runtime-produced artifacts can therefore retain references to existing runtime artifact/evidence refs while the durable workspace stores the actual archived payload.

Provenance is part of the record checksum.

## Storage durability

Artifact Workspace uses a small storage adapter contract:

- `get(key)`
- `set(key,value)`
- `remove(key)`

CHAT 14 includes:

- in-memory adapter for tests;
- Node directory adapter for durable local storage.

The directory adapter persists index, record metadata, and content-addressed payloads outside process/chat memory.

A new workspace instance opening the same directory can verify and read existing artifact versions.

## Workspace index integrity

The persisted workspace index has its own SHA-256.

It contains:

- artifact-version entries;
- append-only artifact events;
- last update timestamp.

Workspace verification validates:

- index checksum;
- artifact event hash chain;
- artifact records;
- payload checksums;
- version ancestry.

Editing or deleting index metadata without a matching checksum is detected.

## Portable workspace bundle

`workspace.exportBundle()` produces a portable artifact bundle.

`importArtifactWorkspaceBundle(...)` verifies before restoring:

- bundle checksum;
- index checksum;
- event hash chain;
- record checksums;
- payload length/checksum;
- record/index identity;
- version ancestry.

Only after validation are records written into the destination storage adapter.

This allows durable transfer/backup without relying on chat history.

## Artifact events

Every stored artifact version appends a canonical workspace event:

`ARTIFACT_VERSION_STORED`

Artifact events carry:

- monotonic sequence;
- timestamp;
- artifact ref;
- Mission / Task / Attempt ownership;
- previous event hash;
- event hash.

The workspace event stream is hash chained.

## Canonical replay stream

`buildReplayStream(...)` accepts:

- Mission;
- TaskNodes;
- Execution Attempts;
- Mission Orchestrator events;
- validated Artifact Workspace events.

Replay events are ordered deterministically by:

1. timestamp;
2. source type;
3. source index.

Each replay event stores:

- stream ID;
- sequence;
- timestamp;
- event kind;
- Mission / Task / Attempt IDs;
- canonical source type;
- source index;
- source-record SHA-256;
- exact source payload;
- previous event hash;
- event hash.

The stream also contains:

- canonical terminal snapshot;
- snapshot SHA-256;
- event count;
- head event SHA-256;
- whole-stream SHA-256.

## Timeline reconstruction

`reconstructTimeline(...)` first validates the complete replay stream.

It then emits structured timeline rows containing:

- sequence;
- timestamp;
- kind;
- Mission / Task / Attempt IDs;
- source type;
- source-record checksum;
- exact canonical facts.

It does **not** add generated prose, inferred motives, invented progress, or a model-written summary.

Therefore:

```text
timeline fact = canonical source payload
timeline != generated narration
```

## Tamper and missing-event handling

Replay validation fails closed on:

- source payload tamper;
- event checksum tamper;
- previous-event hash mismatch;
- sequence gap;
- missing middle event;
- missing tail event via event-count/head mismatch;
- terminal snapshot tamper;
- whole-stream checksum mismatch;
- invalid artifact event stream.

Artifact validation separately rejects:

- payload tamper;
- metadata tamper;
- index tamper;
- broken version ancestry;
- broken ownership.

## Mission archive helper

`archiveMissionRun(...)` binds a completed Mission result to the Artifact Workspace.

It:

1. stores supplied durable artifacts;
2. validates Mission/Task/Attempt ownership;
3. includes canonical workspace artifact events;
4. combines those events with Mission Orchestrator events;
5. builds the replay stream.

This is an archive layer around existing Mission Engine truth.

It does not rewrite Mission execution state or fabricate artifacts that were not supplied.

## Real Mission Engine integration

The integration test runs a real bounded Mission through:

- Mission Planner;
- Mission Orchestrator;
- Runtime Execution Adapter.

The resulting runtime/evidence refs are used as provenance for durable REPORT and EVIDENCE artifacts.

The archive is written to directory-backed storage, replay is validated, and a newly opened workspace verifies the same durable records.

## Scope boundaries

CHAT 14 does not:

- implement checkpoint/recovery semantics from CHAT 15;
- mutate old artifact versions;
- treat an artifact ref as proof the underlying work is correct;
- replace signed execution receipts;
- replace Siti verification;
- use generated narration as replay truth;
- upload artifact data to an external service;
- claim remote/cloud artifact durability.
