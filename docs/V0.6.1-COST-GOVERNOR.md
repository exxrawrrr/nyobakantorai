## Goal

CHAT 13 turns cost from telemetry-only information into an operational execution control.

The implementation reuses existing v0.6 boundaries:

- Mission hard budget: `Mission.budget.hard_limit_amount`;
- Model Router estimated-cost evidence;
- canonical TaskNode approval states;
- Mission Orchestrator dispatch boundary;
- execution receipts / telemetry cost semantics where actual cost may be KNOWN or UNKNOWN.

It does not create a second Mission state machine, approval system, or model router.

## Core package

`packages/cost-governor/index.mjs`

API:

- `normalizeCostPolicy(...)`
- `normalizeCostAmount(...)`
- `normalizeCostLedgerEntry(...)`
- `assessCostAdmission(...)`
- `reconcileCostLedger(...)`
- `createCostGovernor(...)`

Canonical policy:

`config/cost-governor-policy.json`

Schema:

`schemas/cost-governor-policy.schema.json`

The default repository policy defines thresholds but leaves all persistent hard-limit maps unset. This preserves current behavior until an operator explicitly configures spend limits.

## Budget scopes

The governor can enforce concurrent hard budgets for:

- UTC day;
- project;
- mission;
- employee.

A Mission's canonical `budget.hard_limit_amount` is also enforced automatically when Cost Governor is active.

If both the governor policy and Mission specify a Mission limit, the stricter limit wins.

All governed cost uses one configured ISO-like currency. Cross-currency arithmetic is rejected rather than silently converted.

## Threshold semantics

Each configured hard limit has four operational zones:

1. below `warning_ratio` -> `ALLOW`;
2. warning threshold -> `WARN`;
3. reroute threshold -> `REROUTE`;
4. approval threshold -> `APPROVAL_REQUIRED`;
5. hard limit -> `STOP`.

Canonical default ratios:

- warning: 70%;
- reroute: 85%;
- approval: 95%;
- stop: 100%.

These are ratios of the applicable hard limit, not extra budgets.

## Hard-stop rule

An owner approval may authorize spend above the approval threshold only while projected spend remains below the configured hard limit.

Approval never overrides the hard stop.

Therefore:

`approval != permission to exceed hard budget`

## Reroute behavior

A cost admission may include bounded alternative estimates.

At the reroute threshold the governor returns the cheapest known alternative that improves the worst governed utilization.

Mission Orchestrator supports one explicit `resolveCostReroute(...)` callback.

The callback must return a normal runtime resolution with fresh cost-governance metadata. The rerouted resolution is assessed again.

If no admissible reroute is resolved, execution is blocked by policy.

Fallbacks do not bypass hard budgets or unknown-cost rules.

## Approval-required overage

Cost approval reuses canonical TaskNode approval state.

CHAT 13 adds a narrow legal transition:

`READY -> WAITING_APPROVAL`

with:

```json
{
  "required": true,
  "status": "PENDING",
  "approval_ref": null
}
```

Existing resolution semantics remain unchanged:

`WAITING_APPROVAL -> READY`

requires:

- `APPROVED`;
- non-empty `approval_ref`.

This is policy-driven approval escalation, not a second approval system.

## Unknown cost semantics

Unknown cost is never treated as zero.

When a hard budget applies:

- projected cost UNKNOWN -> `STOP`;
- an unresolved UNKNOWN ledger entry in an applicable scope -> `STOP`;
- missing actual-cost reporter after execution -> an UNKNOWN ledger entry is recorded automatically;
- future budgeted work in that scope stops until the unknown spend is reconciled.

This preserves the existing receipt / telemetry truth boundary.

## Actual cost reconciliation

After runtime execution, Mission Orchestrator can call `reportActualCost(...)`.

The reporter may return one or more cost entries.

Each entry can classify spend as:

- `MODEL`;
- `TOOL`;
- `PROVIDER`;
- `OTHER`.

Ledger dimensions include:

- provider ID;
- model ID;
- tool ID;
- project ID;
- mission ID;
- task ID;
- employee ID;
- timestamp;
- evidence references;
- KNOWN / UNKNOWN cost.

Provider/model/tool views are projections over the same ledger entries; they do not create duplicate accounting records.

Monetary aggregation uses normalized decimal arithmetic to avoid binary floating-point drift such as `0.2 + 0.1 = 0.30000000000000004`.

## Post-execution overrun

Actual spend may exceed an estimate.

The governor therefore recomputes budget state after actual-cost recording.

A scope records:

- `hard_limit_breached`;
- `reconciliation_required` for unresolved UNKNOWN entries.

Mission Orchestrator emits explicit reconciliation events.

If all work tasks technically succeeded but cost state contains a hard-limit breach or unresolved unknown, the Mission settles `PARTIAL`, not `SUCCEEDED`.

Completed TaskNodes remain visible as `SUCCEEDED`; the Mission-level cost-integrity failure is not erased.

## Orchestrator integration

When `costGovernor` is supplied to `executeMissionPlan(...)`:

- every runtime resolution must carry `cost_governance`;
- admission occurs before TaskNode enters `RUNNING`;
- `WARN` proceeds but remains recorded;
- `REROUTE` requires a bounded reroute or blocks;
- `APPROVAL_REQUIRED` moves the task to canonical `WAITING_APPROVAL`;
- `STOP` blocks execution;
- actual cost is recorded after each executed attempt;
- missing actual cost becomes UNKNOWN;
- final Mission truth includes unresolved cost integrity.

Without a Cost Governor, existing orchestration behavior is unchanged.

## Events and result surface

- `COST_ADMISSION_RECORDED`;
- `TASK_COST_REROUTED`;
- `TASK_WAITING_COST_APPROVAL`;

- `COST_LEDGER_RECORDED`;
- `COST_RECONCILIATION_REQUIRED`;
- `MISSION_COST_RECONCILIATION_REQUIRED`.

Mission results expose:

- `cost_decisions`;
- `cost_entries`;
- `cost_snapshot`.

These are canonical governor facts, not generated narrative.

## Scope boundaries

CHAT 13 does not:

- fetch vendor pricing dynamically;
- perform FX conversion;
- create billing-provider credentials;
- authorize hard-budget override;
- invent cost for providers that report none;
- implement daily scheduled budget resets outside timestamp-scoped ledger evaluation;
- start CHAT 14 artifact/replay work.
