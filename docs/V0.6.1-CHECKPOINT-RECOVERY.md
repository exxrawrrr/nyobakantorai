## Goal

CHAT 15 enables useful bounded work to resume after recoverable Mission failures without duplicating work that already completed successfully.

The implementation reuses existing canonical state and execution boundaries:

- Mission states already include `RETRYING` and `RECOVERED`;
- TaskNode states already include `RETRYING` and `RECOVERED`;
- Execution Attempt already contains `previous_attempt_id` and `recovery_checkpoint_ref`;
- Artifact Workspace provides durable storage for checkpoint payloads;
- Runtime Execution Adapter remains the only bounded execution boundary;
- Cost Governor, approval, and runtime safety policies remain authoritative during recovery.

CHAT 15 does not introduce a second Mission engine.

## Checkpoint contents

A checkpoint binds:

- Mission snapshot;
- TaskNode snapshots;
- Execution Attempt history;
- completed TaskNode IDs;
- canonical Orchestrator events;
- recovery-cycle number;
- bounded failure reason;
- creation timestamp;
- checkpoint SHA-256;
- content-addressed checkpoint ref.

Reference shape:

```text
checkpoint:sha256:<checkpoint-sha256>
```

The checksum covers the canonical checkpoint body.

Editing Mission, TaskNode, Attempt, completed-task set, events, reason, or recovery cycle without recomputing the exact canonical record fails validation.

## Safe resume boundary

A checkpoint may only be used for resume when the Mission is:

- `PARTIAL`
- `FAILED`
- `BLOCKED`

Recovery fails closed when:

- Mission is not at a supported failure boundary;
- any TaskNode is still `RUNNING`;
- any Execution Attempt is still `RUNNING`;
- checkpoint Mission does not match the plan;
- checkpoint TaskNode set differs from the plan;
- checkpoint checksum does not validate;
- recovery-cycle limit is exhausted.

This prevents replaying a snapshot that may still have live execution in flight.

## Completed-work preservation

TaskNodes already in:

- `SUCCEEDED`
- `VERIFIED`

are recorded in `completed_task_ids`.

During resume they are preserved exactly and excluded from runtime scheduling.

They are not sent to:

- `resolveRuntime()`;
- `resolveRecoveryRuntime()`;
- Runtime Execution Adapter.

This is the central no-duplication invariant.

## Failure and dependency handling

Recoverable failed work follows:

```text
FAILED / PARTIAL / runtime-BLOCKED
        -> RETRYING
        -> RECOVERED
        -> RUNNING
        -> terminal state
```

A task blocked only because an upstream dependency failed is reset to a pending `PLANNED` state.

After the recovered upstream TaskNode succeeds, the dependency-blocked TaskNode becomes `READY` and proceeds normally.

Therefore downstream work is reopened only when its dependency truth is actually restored.

## Attempt lineage

A recovered runtime execution creates a new immutable Execution Attempt.

The new Attempt must contain:

- incremented ordinal;
- `previous_attempt_id`;
- `recovery_checkpoint_ref`.

The failed Attempt is never mutated into success.

Example:

```text
Attempt #1 FAILED
        |
        v
checkpoint:sha256:...
        |
        v
Attempt #2 SUCCEEDED
previous_attempt_id = Attempt #1
recovery_checkpoint_ref = checkpoint
```

## Bounded retry policy

Canonical policy defines:

- `max_attempts_per_task`;
- `max_recovery_cycles`;
- retryable error categories;
- provider fallback allowlists;
- browser session restart limit.

Default repository values:

- max attempts per task: 3;
- max recovery cycles: 2;
- browser restarts: 1.

Retryable error categories currently include bounded runtime classes such as:

- `TIMEOUT`;
- `ADAPTER_ERROR`;
- `CLEANUP_FAILED`;
- `RUNTIME_REPORTED_FAILURE`;
- `RUNTIME_REPORTED_PARTIAL`.

A policy violation or another non-retryable category is not made recoverable merely by changing TaskNode state.

## Provider fallback

Provider fallback is policy-controlled.

The default policy has no configured fallbacks.

When an operator configures:

```json
{
  "provider_fallbacks": {
    "provider-primary": ["provider-fallback"]
  }
}
```

recovery may select only those providers.

The Orchestrator passes recovery metadata to the runtime resolver and validates that the returned adapter provider matches the policy decision.

A resolver cannot silently substitute an unapproved provider.

Provider history is retained from Execution Attempts so future recovery cycles do not accidentally select an already-used fallback when another allowed fallback exists.

## RETRYING / RECOVERED semantics

CHAT 15 activates the existing canonical states instead of inventing new ones.

Mission recovery emits:

- `MISSION_RETRYING`;
- `MISSION_RECOVERED`.

Task recovery emits:

- `TASK_RETRYING`;
- `TASK_RECOVERED`;
- `TASK_RECOVERY_DEPENDENCY_RESET`;
- `TASK_RECOVERY_DEPENDENCY_READY`;
- `RECOVERY_RUNTIME_SELECTED`.

The recovery result also exposes:

- checkpoint ref;
- recovery cycle;
- completed-task IDs;
- retried-task IDs;
- dependency-reset task IDs.

## Browser / session recovery interface

Browser recovery is intentionally conservative.

Canonical strategy:

`NEW_ISOLATED_SESSION`

The recovery request forbids:

- previous-session reuse;
- user-profile reuse;
- credential carry-over.

The opener must return:

- a different `session_ref`;
- `isolated: true`;
- `user_profile_reused: false`;
- `credentials_carried: false`.

Session restart count is bounded by recovery policy.

CHAT 15 does not reconnect to a user's personal browser profile or silently restore authentication.

## Durable checkpoint storage

Checkpoint objects can be persisted as `EVIDENCE` artifacts in the CHAT 14 Artifact Workspace.

The archived payload contains the canonical checkpoint JSON.

Restore validates:

- Artifact Workspace record/payload checksums;
- checkpoint JSON;
- checkpoint SHA-256;
- Mission ownership;
- provenance containing the checkpoint ref.

The checkpoint can therefore survive process/chat memory and be reopened through directory-backed Artifact Workspace storage.

## Recovery and Cost Governor

Recovery does not bypass cost controls.

When Cost Governor is active:

- recovered runtime resolution still requires cost-governance metadata;
- reroute thresholds still apply;
- approval thresholds still apply;
- hard stops still apply;
- actual-cost reconciliation still applies.

A recovery attempt is not privileged spending.

## Failure-injection evidence

CHAT 15 tests inject:

- a mid-Mission runtime failure after an earlier TaskNode already succeeded;
- dependency blocking caused by that failure;
- approved provider fallback;
- an unapproved fallback-provider attempt;
- a bounded runtime timeout;
- an unsafe checkpoint containing RUNNING state.

The main recovery test proves:

1. Task #1 succeeds before the failure;
2. Task #2 fails;
3. Task #3 is dependency-blocked;
4. checkpoint is created;
5. Mission enters RETRYING then RECOVERED;
6. Task #2 retries through the allowed fallback provider;
7. Task #1 is not executed again;
8. Task #3 becomes READY only after Task #2 recovers;
9. Task #3 executes once;
10. Mission finishes SUCCEEDED;
11. retry Attempt points to both the prior Attempt and recovery checkpoint.

## Scope boundaries

CHAT 15 does not:

- make policy violations automatically retryable;
- override Cost Governor;
- override owner approvals;
- retry forever;
- reuse an unsafe RUNNING snapshot;
- mutate an old Execution Attempt;
- carry browser credentials/profile into a fresh session;
- implement Project Brain / Memory 2.0 from CHAT 16.
