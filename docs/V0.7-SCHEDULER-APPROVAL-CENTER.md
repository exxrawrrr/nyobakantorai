## Goal

CHAT 20 adds recurring work without creating a second execution authority.

The core rule is:

```text
scheduled trigger
!= execution permission
!= cost approval
!= mutation approval
!= verified result
```

A due schedule may only materialize work through the existing Mission Engine.

## Scheduler contract

Implementation:

`packages/scheduler-approval-center/index.mjs`

A recurring schedule binds:

- schedule ID;
- objective;
- ACTIVE / PAUSED / REVOKED / EXPIRED state;
- DAILY or WEEKLY cadence;
- cadence interval;
- exact local time window;
- IANA timezone;
- mission hard budget;
- risk class;
- constraints;
- required evidence;
- work-item blueprint;
- start time;
- optional expiry;
- optional max run count.

Schedules are content-addressed:

`schedule:sha256:<digest>`

## Time and cadence safety

Schedule due checks are timezone-aware through `Intl.DateTimeFormat`.

The scheduler evaluates:

- schedule state;
- start time;
- expiry;
- max runs;
- local time window;
- daily/weekly interval;
- weekly day selection;
- duplicate trigger on the same local calendar day.

The Morning Briefing fixture proves that:

`07:30 Asia/Jakarta`

is inside the configured 07:00–09:00 window even though the underlying timestamp is UTC.

## Normal Mission Engine only

`materializeScheduledMission(...)` does not define a special scheduled Mission type.

When a trigger is admitted it calls the canonical:

`planMission(...)`

The resulting Mission:

- starts in `PLANNED`;
- uses normal TaskNodes;
- uses normal risk classification;
- uses normal task approval policy;
- uses `GUARDED` autonomy;
- carries its normal Mission hard budget;
- carries required evidence;
- records the schedule reference and trigger timestamp as constraints.

The Schedule Run is merely provenance around that normal Mission Plan.

## Cost Governor gate

Before Mission materialization, the scheduler calls:

`assessCostAdmission(...)`

using the existing Cost Governor.

Only these states may materialize a Mission:

- `ALLOW`;
- `WARN` — including an already reviewed cost approval below the hard limit.

These states block the schedule:

- `REROUTE`;
- `APPROVAL_REQUIRED`;
- `STOP`.

This is deliberate.

A schedule does not have authority to choose a cheaper provider/model alternative itself and cannot convert “approval required” into permission just because the trigger time arrived.

Unknown/unreconciled cost also fails closed through the Cost Governor.

## Approval Center 2.0 data contract

Approval Request v2 explicitly carries:

- target;
- risk;
- budget;
- reason;
- evidence;
- preview;
- scope;
- request time;
- expiry.

Request records are content-addressed:

`approval-request:sha256:<digest>`

Wildcards are forbidden in approval resources.

## Human decisions

Only the human owner may record:

- `APPROVED`;
- `EDITED`;
- `REJECTED`.

An EDITED approval may only narrow the original request:

- actions may be removed but not added;
- resources may be removed but not added;
- expiry may be shortened but not extended;
- edited preview is required.

Approval decisions are content-addressed:

`approval-decision:sha256:<digest>`

## Scope and expiry at point of use

`authorizeWithApproval(...)` checks the approval again when an action is about to use it.

It rejects:

- rejected approval;
- expired approval;
- action outside approved scope;
- resource outside approved scope.

Approval therefore cannot be treated as a permanent reusable token.

## Office Approval Center 2.0 UI

The existing local Office approval view now surfaces:

- Target;
- Risk;
- Budget;
- Reason;
- Evidence;
- Preview;
- Scope;
- Expiry.

The owner may:

- Approve;
- Edit scope / preview;
- Reject.

Legacy registry tasks remain schema 3 for compatibility, but Approval Center v2 metadata is added as bounded optional fields.

Only the owner can edit approval reason/preview/scope/expiry/budget.

Exact resources are required; wildcard resources are rejected.

Once a local task is approved, the approved scope cannot be silently edited in place. A new approval must be created for materially changed scope.

If an approval has an expiry, local task execution is blocked once that expiry is reached.

Runtime claims remain read-only and cannot be approved or edited from the local Office UI.

## Existing approval/evidence boundaries remain authoritative

Approval Center 2.0 does not replace:

- risk classification;
- Capability Router grants;
- Connector Center grants;
- Browser Agent mutation plans;
- Cost Governor;
- execution receipts;
- evidence verification;
- independent QA.

The same trust boundary remains:

```text
human permission
!= technical capability
!= actual execution
!= verified result
```

## Evidence boundary

CHAT 20 is repository/deterministic execution evidence.

It does not claim that a production scheduler daemon is running continuously, that a real morning briefing has been delivered, or that a live external write has been approved/executed.

Live connected scheduled-work evidence remains a CHAT 22 requirement.
