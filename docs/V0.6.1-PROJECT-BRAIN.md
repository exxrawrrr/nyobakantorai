## Goal

CHAT 16 adds project knowledge that remains useful across work while preserving the existing profile-memory isolation boundary.

Memory 2.0 extends the existing `packages/memory-learning` domain. It does not create a second authority system and it does not make remembered content equivalent to evidence, execution, permission, approval, or verification.

## Scope model

Project Brain has exactly three runtime scopes:

```text
PRIVATE
  -> PROJECT
  -> APPROVED_SHARED
```

Scope widening is monotonic and explicit.

- `PRIVATE`: visible only to the employee owner.
- `PROJECT`: visible only to employees whose read request carries the exact project grant.
- `APPROVED_SHARED`: visible only to requests carrying the exact approved shared scope.

A project grant never implies access to private memory. A project grant also does not imply access to `APPROVED_SHARED` memory.

## Knowledge classes

Records support:

- decisions;
- facts;
- assumptions;
- failures;
- preferences;
- terminology;
- artifacts;
- lessons.

Each record contains:

- source references;
- evidence references when available;
- confidence;
- creation time;
- optional expiration;
- retention label;
- owner;
- scope;
- sensitivity;
- provenance;
- immutable content checksum;
- content-addressed memory reference.

Reference shape:

```text
memory:sha256:<record-sha256>
```

## Promotion and attribution

A record cannot silently become broader memory.

Promotion is:

```text
PRIVATE
  -- explicit review -->
PROJECT
  -- explicit review -->
APPROVED_SHARED
```

Every promotion creates a new immutable record. The prior record remains unchanged.

The promoted record must contain:

- previous scope;
- parent record reference;
- reviewer identity;
- approval timestamp;
- promotion reason;
- parent record in `supersedes`;
- parent record in provenance.

The underlying knowledge payload cannot change during scope promotion. A record that changes the claim while claiming to be a promotion fails lineage validation.

## Access semantics

`buildProjectMemoryView(...)` evaluates every candidate record independently and fails closed.

It denies:

- cross-profile PRIVATE reads;
- PROJECT reads without exact project grant;
- APPROVED_SHARED reads without exact shared scope;
- expired records;
- malformed/checksum-invalid records;
- promoted records whose parent is missing;
- promotion chains whose parent scope does not match;
- promotions that altered underlying knowledge.

## Durable local storage

`createProjectBrainStore(...)` provides an immutable indexed record store over a minimal `get/set/remove` storage contract.

The Node adapter:

`packages/memory-learning/project-brain-node-storage.mjs`

provides directory-backed storage with atomic file replacement.

The store validates:

- record checksum;
- record reference;
- record-id immutability;
- promotion ancestry;
- index checksum.

A reopened store can reproduce the same granted view without relying on chat/process memory.

## Existing Memory 1.x compatibility

Existing M0-M4 learning contracts remain intact.

CHAT 16 does **not** automatically convert M1/M2 profile learning into Project Brain records.

This is intentional: automatic conversion would create a scope-widening path outside explicit promotion.

Legacy M3 shared knowledge remains governed by its existing `shared_scope` contract. New Memory 2.0 records use the stricter PRIVATE -> PROJECT -> APPROVED_SHARED chain.

## Secrets and private sensitivity

Secret-like content remains prohibited.

`SECRET_PROHIBITED` cannot be persisted.

Records classified with `sensitivity: PRIVATE` may remain PRIVATE but cannot be widened to PROJECT or APPROVED_SHARED.

## Authority boundary

Project Brain memory is context, not authority.

A memory record does not prove:

- a provider is connected;
- a capability grant exists;
- an external action executed;
- an approval exists;
- an artifact is verified;
- a fact is still current.

Consequential or time-sensitive facts must be rechecked through the normal evidence/verification path.
