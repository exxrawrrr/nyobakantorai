# v0.6 Capability Router / Tool Policy — CHAT 06

Status: **IMPLEMENTED FOR SCOPED ACTION-AUTHORIZATION LAYER**  
Date: 2026-10-01  
Baseline: `main@2056ca98fc78f7ffecb251b139deccac29561093`

CHAT 06 extends the existing `packages/capability-router/`.

It does **not** add a duplicate Tool Router.

The goal is to turn a broad capability contract into a concrete, auditable action route that binds:

- employee;
- capability;
- action;
- READ/WRITE mode;
- exact target resource;
- provider connection evidence;
- resource grant evidence;
- autonomy;
- approval state/evidence;
- required execution evidence.

The route decision is authorization evidence only.

It is not proof that a tool ran.

## 1. Existing boundary preserved

CHAT 06 keeps these existing responsibilities:

- `config/capabilities.json` — capability catalog and base risk metadata;
- employee `operational_contract.capability_scope` — broad worker capability scope;
- provider snapshots — connection-state evidence;
- existing `authorize()` / `authorizeForEmployee()` APIs — backward compatible;
- `packages/mission-engine/` — orchestration;
- `packages/runtime-execution-adapter/` — bounded runtime execution.

New action routing is added inside the same capability-router package.

## 3. Policy layers

Authorization is intentionally layered.

```text
employee capability scope
        ↓
exact resource grant
        ↓
provider connection evidence
        ↓
access mode + capability risk
        ↓
autonomy policy
        ↓
approval status/evidence
        ↓
authorized capability route
```

A later layer cannot override failure at an earlier layer.

## 4. Employee scope

The employee's existing:

```text
operational_contract.capability_scope
```

remains the broad worker boundary.

If a capability is not in that scope:

```text
WORKER_CAPABILITY_OUT_OF_SCOPE
```

is returned before provider resolution.

A resource grant cannot expand a worker beyond the employee contract.

## 5. Exact resource grants

CHAT 06 adds Capability Resource Grant v1.

A grant binds:

- grant ID;
- employee ID;
- capability ID;
- allowed access modes;
- allowed actions;
- exact resource targets;
- issue time;
- optional expiry;
- grant evidence reference.

Example shape:

```json
{
  "schema": 1,
  "grant_id": "grant-example",
  "employee_id": "maya",
  "capability_id": "ads.meta.read",
  "access_modes": ["READ"],
  "actions": ["inspect"],
  "targets": [
    {
      "resource_type": "ad_account",
      "resource_id": "account-example"
    }
  ],
  "issued_at": "2026-10-01T09:00:00.000Z",
  "expires_at": null,
  "evidence_ref": "grant-evidence:example"
}
```

v1 does not support wildcard targets.

That is deliberate.

Broad/wildcard grants require a separate policy review rather than silently expanding target scope.

## 6. Safe default

Repository default:

```text
config/capability-grants.json
grants = []
```

No real resource grants are committed.

A trusted deployment/runtime policy layer must provide reviewed grants with evidence.

Therefore a fresh install fails closed for resource-scoped tool actions.

## 7. READ vs WRITE

CHAT 06 defines:

```text
READ
WRITE
```

as explicit action access modes.

A `READ_ONLY` capability cannot be routed as `WRITE`.

High-impact capability metadata remains conservative.

For capabilities already classified above READ_ONLY, existing risk/approval requirements are preserved even if the requested action is descriptive.

CHAT 06 does not silently downgrade catalog risk based on free-form action text.

## 8. Connection evidence

A route still requires:

```text
connection.state = CONNECTED
connection.evidence_ref != null
```

A disconnected provider cannot produce an authorized action route.

This preserves:

```text
installed/known capability
!=
connected capability
!=
authorized action
```

## 9. GUARDED writes

A GUARDED high-impact/write route requires:

```text
approval_status = APPROVED
approval_ref != null
```

`APPROVED` without approval evidence remains blocked:

```text
APPROVAL_EVIDENCE_REQUIRED
```

This closes a gap between a status claim and durable approval evidence.

## 10. OBSERVE mode

OBSERVE cannot authorize high-impact/write actions.

Even when all of these are present:

- employee scope;
- exact resource grant;
- CONNECTED provider;
- approval.

The decision remains:

```text
OBSERVE_MODE_NO_WRITES
```

## 11. DELEGATED mode

DELEGATED does not replace resource grants.

A delegated action must satisfy both:

- capability is inside `delegatedCapabilities`;
- exact employee/action/resource grant exists.

Therefore:

```text
delegated capability
!=
unbounded resource permission
```

## 12. Evidence requirements

Authorized READ route requires:

```text
CONNECTION_EVIDENCE
RESOURCE_GRANT_EVIDENCE
RESULT_EVIDENCE
```

Authorized WRITE route requires:

```text
CONNECTION_EVIDENCE
RESOURCE_GRANT_EVIDENCE
APPROVAL_EVIDENCE
PRE_ACTION_STATE
EXECUTION_RECEIPT
POST_ACTION_STATE
```

These are execution evidence requirements.

Their presence in a route does not claim that the evidence already exists.

## 13. Capability route reference

An allowed action route receives:

```text
capability-route:sha256:<64 hex>
```

The digest binds:

- employee;
- capability/risk;
- action;
- access mode;
- exact target;
- connection provider/evidence/timestamp;
- resource grant/evidence/timestamps;
- autonomy;
- approval state/evidence;
- required evidence;
- authorization decision.

`validateCapabilityRouteDecision(...)` recomputes the digest.

Tampered route content is rejected.

## 14. Orchestrator integration

`bindCapabilityRoutesToRuntime(...)` accepts only routes that are:

- `allowed=true`;
- digest-valid;
- backed by CONNECTED evidence.

It then supplies exact:

```text
capability_route_refs
```

to the existing CHAT 04 runtime resolution.

Execution Attempt records preserve those refs.

Blocked, waiting-approval, disconnected, or tampered routes cannot be bound into runtime resolution.

This proves:

```text
capability route decision
        ↓
runtime resolution
        ↓
Execution Attempt capability_route_refs
```

without pretending that the route decision itself proves execution.

## 15. Important separation from runtime capabilities

Business/tool capabilities:

```text
ads.meta.read
ads.meta.write
browser.structured
...
```

are not the same as runtime-adapter capabilities such as:

```text
model_inference
temporary_workspace
evidence_collection
```

CHAT 06 keeps the two namespaces separate.

The orchestrator runtime contract still controls its own runtime capability allowlist.

## 16. Failure reasons

New fail-closed reasons include:

- `RESOURCE_GRANT_MISSING`
- `TARGET_RESOURCE_OUT_OF_SCOPE`
- `RESOURCE_GRANT_EXPIRED`
- `ACCESS_MODE_INCOMPATIBLE_WITH_CAPABILITY`
- `APPROVAL_EVIDENCE_REQUIRED`

Existing reasons remain valid, including:

- `WORKER_CAPABILITY_OUT_OF_SCOPE`
- `CAPABILITY_NOT_CONNECTED`
- `OBSERVE_MODE_NO_WRITES`
- `OUTSIDE_DELEGATED_SCOPE`
- `OWNER_APPROVAL_REQUIRED`

## 17. Backward compatibility

The original capability-router APIs remain:

- `resolve()`;
- `authorize()`;
- `authorizeForEmployee()`.

Existing tests remain green.

CHAT 06 adds:

- `authorizeActionForEmployee()`;
- `validateCapabilityRouteDecision()`;
- `bindCapabilityRoutesToRuntime()`.

## 18. What CHAT 06 does not do

CHAT 06 does not:

- call Meta/Google/browser APIs;
- discover live provider resources;
- create real resource grants;
- auto-approve writes;
- treat capability route evidence as execution evidence;
- replace signed execution receipts;
- merge capability authorization with Model Router policy;
- implement public sandbox quotas;
- add wildcard resource grants.
