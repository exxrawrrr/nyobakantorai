## 2. Mission Plan v1

A Mission Plan is a planning artifact containing:

- one normalized Mission;
- one or more canonical TaskNode candidates;
- per-node planning metadata;
- dependency edges;
- topological layers;
- parallel groups;
- roots/leaves;
- routing decisions;
- assumptions;
- unknowns;
- generation timestamp.

The Plan is not execution evidence.

No TaskNode produced by the planner is marked `RUNNING`, `SUCCEEDED`, or `VERIFIED`.

## 3. Planner strategies

### `RULE_BASED_V1`

Used when the objective contains enough deterministic planning signal.

Current bounded decomposition creates:

1. source/evidence collection;
2. domain analysis;
3. synthesis;
4. independent verification.

The first two tasks may run in parallel because neither depends on the other.

This is intentionally a **small deterministic baseline**, not a claim of general autonomous planning intelligence.

### `EXPLICIT_WORK_ITEMS`

Used when the caller supplies explicit work items and dependency keys.

This path still:

- validates dependencies;
- routes employees through `routeWork()`;
- propagates constraints/evidence/budget;
- builds/validates the DAG;
- rejects cycles.

Human employee assignment remains authoritative because `routeWork(..., assignedId)` already treats it as the winning signal.

### `COORDINATOR_FALLBACK`

Used when the objective does not contain enough deterministic planning signal.

The planner returns one Praroro/coordinator task plus an explicit unknown explaining that safe multi-step decomposition was not justified.

This is a truth-preserving fallback.

It is preferred over inventing a complex task graph from weak signals.

## 4. Worker assignment

Employee selection is not implemented again inside Mission Planner.

Planner calls:

```text
lib/routing.mjs -> routeWork(...)
```

Inputs may include:

- task text;
- required skills;
- human assignment;
- workload;
- task risk class;
- bounded historical routing signal.

The resulting route decision is stored in Plan metadata with:

- employee;
- route source;
- score;
- reasons;
- factors.

A route decision is planning evidence, not proof that the employee executed the task.

## 5. Constraint propagation

Global Mission constraints are propagated to every planned node.

Node-local constraints may add stricter requirements.

Example:

```text
Mission:
  - read-only planning
  - do not change production website

Task:
  - collect source evidence

Task effective constraints:
  - read-only planning
  - do not change production website
  - [any node-specific constraint]
```

## 6. Evidence requirement propagation

Mission-level required evidence is combined with node-specific evidence requirements.

Example:

```text
Global:
  - source URLs

Evidence collection task:
  - source provenance
  - retrieval evidence

Effective:
  - source URLs
  - source provenance
  - retrieval evidence
```

These are requirements for later execution.

They are not populated into TaskNode `evidence_refs` because planning has not produced evidence yet.

## 7. Budget propagation

Mission budget is canonical on Mission.

Each node receives planning metadata:

```json
{
  "source": "MISSION_SHARED",
  "hard_limit_amount": 5,
  "currency": "USD"
}
```

CHAT 03 does not divide budget automatically between workers.

Reason:

arbitrary per-task budget allocation without cost/runtime knowledge would create false precision.

The full Cost Governor remains a later milestone.

## 8. Dependency graph

Graph edges use:

```text
dependency -> dependent
```

Example:

```text
collect evidence ----\
                     -> synthesis -> verification
domain analysis -----/
```

The graph validator fails closed on:

- unknown dependency node;
- unknown dependent node;
- self dependency;
- duplicate edge;
- cycle;
- duplicate TaskNode ID.

## 9. Topological layers and parallel work

The validator calculates topological layers.

Canonical fixture:

```text
Layer 1:
  collect evidence
  domain analysis

Layer 2:
  synthesis

Layer 3:
  independent verification
```

A layer with more than one task becomes a `parallel_group`.

This only means the tasks are dependency-independent.

It does **not** yet mean CHAT 03 executes them concurrently.

Actual orchestration belongs to CHAT 04.

## 10. Runnable frontier

`readyTaskIds(plan, completedTaskIds)` calculates which TaskNodes have all dependencies satisfied.

Example:

```text
completed: []
ready:
  - evidence
  - domain

completed:
  - evidence
  - domain

ready:
  - synthesis

completed:
  - evidence
  - domain
  - synthesis

ready:
  - verification
```

The helper rejects a completed task ID that is not in the Plan.

## 11. Assumptions and unknowns

Planner output keeps both arrays explicit.

Examples of assumptions:

- evidence collection and domain analysis can start independently;
- synthesis depends on both;
- verification depends on synthesis.

Examples of unknowns:

- analytics access is not known yet;
- final runtime/model/tool choice is intentionally unresolved;
- completeness of external evidence is unknown before execution.

These fields exist so the Plan does not silently turn uncertainty into fact.

## 12. High-impact work

A high-impact plan may create TaskNodes with:

```text
state = PLANNED
approval.required = true
approval.status = PENDING
```

The planner does not approve the task and does not move it into execution.

CHAT 02 approval/state rules remain authoritative.
