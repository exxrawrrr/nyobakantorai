# v0.6 Architecture Lock — Live Workforce Baseline Audit

Status: **ACCEPTED FOR CHAT 01**  
Baseline audited: `main@218612caf33c690fda2be46bd13569a97cb3a01f`  
Date: 2026-10-01  
Behavior change: **none**

This document is the architecture review required by CHAT 01 of the Live Workforce plan.

Its purpose is to prevent v0.6 from inventing parallel task, approval, evidence, runtime, or routing systems when the repository already contains working boundaries for those concerns.

## 1. Executive decision

v0.6 will add a **Mission layer above the existing task/execution/evidence machinery**.

It will **not** replace the current task truth model with a new independent task store.

The core ownership decision is:

```text
Mission / DAG orchestration
        |
        v
canonical Task domain
        |
        +--> authorization / capability policy
        +--> bounded runtime execution
        +--> signed execution receipt
        +--> evidence verification
        +--> task-level independent verification
        |
        v
UI / projections / runtime reconciliation
```

The canonical future task-domain core is `packages/task-registry/`.

`office/registry.mjs` remains a local UI/storage compatibility projection until a reviewed migration is implemented. It is **not** a second canonical v0.6 task domain.

The owner/manual Hermes tooling under `operations/` remains compatibility/operator tooling. It is not promoted into the new Mission Engine.

## 3. Domain ownership ADR summary

The full ADR is in:

`docs/ADR-0001-LIVE-WORKFORCE-DOMAIN-OWNERSHIP.md`

Ownership is locked as follows.

### Mission

Owner: future `packages/mission-engine/`.

Mission owns:

- mission identity;
- objective and constraints;
- plan/DAG;
- TaskNode references;
- dependency graph;
- mission-level budget/autonomy envelope;
- orchestration/retry/cancellation summary;
- mission-level aggregate state.

Mission does **not** own task verification semantics, approval authority, connector connection state, or cryptographic evidence verification.

### TaskNode

Owner: `packages/task-registry/`.

The v0.6 TaskNode is an evolution/versioned extension of the existing canonical task domain.

It owns:

- task identity;
- assignee;
- task lifecycle;
- risk class;
- approval state/ref;
- runtime binding refs;
- receipt refs;
- evidence refs;
- independent verification transition.

A Mission references TaskNode IDs. It does not maintain a separate competing task lifecycle.

### Attempt

Owner: Mission orchestration layer, implemented over `packages/runtime-execution-adapter/`.

An Attempt records one execution try for one TaskNode.

It owns:

- attempt ID;
- task ID;
- selected runtime/model route;
- selected capability route;
- start/end time;
- normalized runtime outcome;
- error category;
- cleanup state;
- receipt ref;
- retry relationship.

The runtime execution adapter remains responsible for executing and normalizing one bounded attempt.

### Evidence

Owners:

- execution authenticity/provenance: `packages/execution-receipt/`;
- evidence decision: `packages/evidence-verifier/`;
- evidence maturity/claim class: `packages/evidence-classification/`;
- durable references: TaskNode / Attempt / later Artifact Workspace.

Mission is not an evidence verifier.

### Approval

Owners:

- task/risk approval state: `packages/task-registry/`;
- capability authorization calculation: `packages/capability-router/`;
- human review projection: office approval UI/summary.

Mission may aggregate “2 approvals pending”, but approval remains scoped to concrete tasks/actions/resources.

## 6. Duplicate-task migration rule

The repository currently has two task representations.

### Canonical core

`packages/task-registry/registry.mjs`

Strengths:

- broader lifecycle states;
- runtime staging;
- receipt attachment/replay protection;
- owner approval;
- independent VERIFIED requirement;
- provider-neutral employee source.

### UI compatibility model

`office/registry.mjs`

Strengths:

- browser-local comments/attachments;
- provenance/quarantine;
- UI-friendly schema;
- storage bundle integration.

Weakness:

- it duplicates lifecycle/approval semantics and can drift from the canonical package.

### Locked migration direction

1. Do not create a third task schema.
2. CHAT 02 defines the next versioned canonical Mission/Task contract around `packages/task-registry`.
3. Preserve office local data with explicit backup/migration/adapter behavior.
4. Office-only fields such as comments/attachments/quarantine become projection/metadata or are mapped explicitly; they must not silently redefine task truth.
5. Runtime provider task IDs such as Hermes `t_...` remain provider/runtime references, not canonical Mission TaskNode IDs.
6. `operations/workflow` six-role routing is not upgraded into Mission Planner; future planner uses the canonical 16-person workforce and `lib/routing.mjs`.

## 7. Runtime and public-demo trust rule

The current `office/server.mjs` is built around:

- localhost Host/Origin checks;
- same-origin mutation defense;
- no dispatch endpoint;
- read-only runtime observation.

v0.6 must not weaken that server simply to ship a public demo.

The public demo should consume shared portable packages while using its own internet-facing session/rate/sandbox boundary.

Exact topology is deferred to CHAT 08.

## 8. Invariants that future chats must preserve

1. `VERIFIED` still requires independent evidence and permitted reviewer policy.
2. Signed receipt authenticity is not external correctness.
3. Approval is permission, not execution proof.
4. Connection is not authorization.
5. Runtime observation stays separate from runtime execution.
6. Public demo synthetic work cannot become real-world evidence.
7. Mission aggregate state cannot override a TaskNode's stricter state.
8. Mission cannot approve its own work.
9. Model/tool routing cannot bypass employee scope, autonomy, risk, approval, or privacy.
10. Unknown cost remains unknown; it cannot be normalized to zero.
11. Local UI storage must not become a second source of runtime truth.
12. Provider task IDs are references, not canonical task IDs.
13. No new package boundary without an explicit delete test.

## 9. CHAT 02 handoff

CHAT 02 may now proceed with a bounded objective:

**define versioned Mission + TaskNode + Attempt schemas/state semantics while reusing the canonical task domain and preserving an explicit office compatibility migration path.**

CHAT 02 should not:

- add a Model Router;
- expose public live endpoints;
- delete office local storage;
- mutate external runtimes;
- merge manual Hermes operations into the Mission Engine.
