## 3. Mission v1

Mission is an aggregate/orchestration object.

Required fields include:

- mission ID;
- objective;
- constraints;
- risk class;
- budget envelope;
- autonomy envelope;
- canonical TaskNode IDs;
- artifact/evidence/approval references;
- state;
- timestamps.

Mission does not contain worker execution logic.

### Mission state catalog

```text
PLANNED
READY
RUNNING
WAITING_APPROVAL
BLOCKED
PARTIAL
FAILED
RETRYING
RECOVERED
SUCCEEDED
VERIFIED
CANCELLED
```

### Mission state meaning

| State | Meaning |
| --- | --- |
| `PLANNED` | Mission exists but is not ready to execute. |
| `READY` | Planning/constraints are sufficient for execution to begin. |
| `RUNNING` | One or more mission tasks are actively executing. |
| `WAITING_APPROVAL` | Mission progress is waiting on one or more required human approvals. |
| `BLOCKED` | Progress cannot continue because of a dependency/policy/runtime/input blocker. |
| `PARTIAL` | Some useful work completed, but the mission did not satisfy the success condition. |
| `FAILED` | Mission failed its current execution path. |
| `RETRYING` | Mission is preparing or entering another bounded execution try. |
| `RECOVERED` | Recovery/checkpoint restoration succeeded; execution may resume. |
| `SUCCEEDED` | Required execution work succeeded but independent verification is not yet implied. |
| `VERIFIED` | Required task verification/evidence is satisfied for the mission claim. |
| `CANCELLED` | Human/system policy intentionally stopped the mission. |

### Critical Mission transition rules

- `PLANNED -> RUNNING` is forbidden; mission must become `READY` first.
- `WAITING_APPROVAL -> READY` requires explicit `approvals_satisfied=true`.
- `SUCCEEDED -> VERIFIED` requires verified required-task evidence plus evidence references.
- `VERIFIED -> RUNNING` requires explicit reopen and owner authority.
- `FAILED/PARTIAL` do not jump directly to success; recovery proceeds through retry/recovery states.
- `CANCELLED` is terminal.

## 4. TaskNode v1

TaskNode is the v0.6 versioned evolution of the canonical task domain.

It is **not** a second Mission-owned task store.

Required fields include:

- canonical task ID;
- optional Mission ID;
- title/objective;
- canonical employee ID;
- risk class;
- state;
- approval state/reference;
- execution Attempt IDs;
- evidence references;
- signed receipt references;
- blocking metadata;
- optional legacy migration metadata;
- timestamps.

### TaskNode state catalog

```text
PLANNED
READY
RUNNING
WAITING_APPROVAL
BLOCKED
PARTIAL
FAILED
RETRYING
RECOVERED
SUCCEEDED
VERIFIED
CANCELLED
```

### Important TaskNode rules

- High-impact required approval blocks `RUNNING` until both `APPROVED` and an approval reference exist.
- The approval decision and `WAITING_APPROVAL -> READY` transition are applied atomically so no invalid “approved but still waiting” snapshot is created.
- `VERIFIED` requires evidence plus an independent reviewer allowed by the canonical employee verification policy.
- Self-verification remains rejected.
- Reopening `VERIFIED` requires explicit `reopen=true` and owner authority.
- `PARTIAL` or `FAILED` moves to `RETRYING`; it does not mutate a failed Attempt into success.
- Receipt references must remain canonical `receipt:sha256:<digest>` values.

## 5. Execution Attempt v1

An Attempt is **one execution try for one TaskNode**.

It is deliberately narrower than TaskNode/Mission state.

Attempt state catalog:

```text
PLANNED
RUNNING
BLOCKED
PARTIAL
FAILED
SUCCEEDED
CANCELLED
```

There is no Attempt-level:

- `RETRYING`;
- `RECOVERED`;
- `VERIFIED`.

Reason:

- retry creates a **new Attempt** linked with `previous_attempt_id`;
- recovery belongs to Task/Mission orchestration;
- verification belongs to Task/evidence semantics, not one runtime try.

Attempt records:

- attempt ID;
- task ID;
- ordinal;
- runtime identity;
- future model-route reference;
- capability-route references;
- start/finish timestamps;
- error category;
- cleanup outcome;
- receipt reference;
- evidence/artifact references;
- previous attempt;
- recovery checkpoint reference.

A `SUCCEEDED` Attempt requires successful cleanup.

`FAILED`, `PARTIAL`, and `BLOCKED` require an explicit error category.

## 6. Runtime execution compatibility

CHAT 02 does not execute models.

The helper `attemptFromRuntimeOutcome(...)` converts an already-produced `runtime-execution-adapter` outcome into an immutable Attempt record.

It does not call the runtime again.

This preserves the existing boundary:

```text
runtime-execution-adapter
  -> normalized bounded outcome
  -> Execution Attempt record
  -> TaskNode orchestration
  -> independent verification
```

## 7. Legacy task migration

`migrateLegacyTaskToTaskNode(...)` provides a fail-closed compatibility projection.

It does not mutate the original v0.5 registry.

### Package-registry mapping

| v0.5 lifecycle | TaskNode v1 |
| --- | --- |
| `PLANNED` | `PLANNED` |
| `REQUESTED` | `READY`, or `WAITING_APPROVAL` when required approval is still pending |
| `IN_PROGRESS` | `RUNNING` |
| `WAITING_FOR_USER` | `WAITING_APPROVAL` only when pending approval is explicit; otherwise `BLOCKED / USER_INPUT` |
| `COMPLETED` | `SUCCEEDED` |
| `VERIFIED` | `VERIFIED` |
| `BLOCKED` | `BLOCKED` |

The key truth rule is:

**legacy `WAITING_FOR_USER` is not assumed to mean approval.**

Unknown/user-input waiting state is preserved as a generic block instead of inventing authorization semantics.

### Office schema-3 mapping

The office local/UI record can be projected into TaskNode v1.

UI-only fields such as comments, attachments, presentation provenance, and quarantine are **not promoted into canonical execution truth** by the TaskNode migration function.

The existing browser data is not deleted in CHAT 02.
